IRTBoss Explainers · Part 10 of 12

The software: every moving part

  • Maintainer

Parts 3–8 explained what gets computed. This part explains where, by whom, and why the pieces are arranged the way they are. The organising idea is the same honesty principle from Part 1, applied to infrastructure: a failure should say what actually went wrong, at the layer it went wrong, and no state should ever silently pretend to be another.

The shape: one image, two processes

The backend is a single Docker image run as two different processes. The API (FastAPI, served by uvicorn) handles HTTP — auth, uploads, run creation, results. The worker (an RQ worker, python -m app.workers.main) executes analyses. They share the image so they cannot drift: a worker running older estimation code than the API would produce results the API cannot describe, and the engine version stamped on every run would then be a lie. Around them sit three stores — PostgreSQL for durable state, Redis for the job queue, and object storage for uploaded files — plus the React frontend, deployed separately as a static site on Vercel.

Why estimation never runs in the web process

The API is async: nothing CPU-bound or blocking is allowed on its event loop, because minutes of numpy in a request handler would freeze every other user's requests behind one person's dataset. So backend/app/workers/tasks.py opens with the rule — this is the only place estimation runs — and the codebase enforces it structurally rather than by convention: the API imports the numerical engine only inside functions (lazily, for things like validating model names), so the web process never even loads numpy at startup. Blocking-but-cheap work in the API — CSV parsing, file writes — is pushed to threads.

Signing in: Argon2id and a signed cookie

Accounts are email and password, nothing federated. Passwords are hashed with Argon2id (64 MiB memory cost, three passes) — a memory-hard function chosen so bulk offline guessing is expensive on the attacker's hardware, not just yours. Two details are worth knowing because they answer questions you will eventually be asked:

  • Sessions are signed tokens, not database rows. The cookie holds an itsdangerous-signed payload of the user id plus a 16-hex fingerprint of the current password hash. Because the fingerprint is checked on every request, changing your password instantly invalidates every session everywhere — with no server-side session table to maintain. Cookies are HttpOnly, SameSite=Lax, and Secure everywhere except in an environment explicitly named as local development, with a 12-hour lifetime. A second, deliberately readable cookie holds a CSRF token that state-changing requests have to echo in a header, and POST /auth/revoke-sessions ends every session for the account by stamping it with a time before which no token is accepted.
  • Login failures are deliberately uninformative, at some cost. One 401 message covers wrong password and unknown email, and an unknown email still pays for a full Argon2 verification against a dummy hash so response timing cannot distinguish the two. (Registration, which must say “taken”, does disclose registered addresses — a documented trade-off, not an oversight.)

Every table a user can reach carries an owner_id — copied down onto datasets and runs deliberately, so ownership is one predicate on the row being read rather than a chain of joins someone can forget. Asking for another user's run returns 404, not 403: the API declines to confirm the id exists at all.

The upload: refused early, stored by reference

A dataset arrives as a CSV via POST /projects/{id}/datasets. Before anything touches the database:

  1. Size is enforced on arrival, not on promise. The body is read in 1 MiB chunks and aborted the moment the running total passes 25 MiB — the declared Content-Length is not trusted. Too big is HTTP 413.
  2. Shape is enforced next — at most 100,000 rows and 1,000 columns — and the declared ID and grouping columns must actually exist. Malformed is HTTP 422, with messages authored by this codebase rather than leaked from a parser.
  3. The bytes are fingerprinted (SHA-256) and stored under a fresh key — datasets/<uuid>.csv, never the client's filename. The checksum lands in the database next to the size, so “is this the same file?” has an answer forever.

What the database stores for the file's location is a storage reference, not a path: local:datasets/<uuid>.csv in development, s3://bucket/key in production. The reason is a failure mode worth spelling out. The API writes the CSV; the worker reads it — a different process, in production possibly a different machine. If the database held a filesystem path, the moment those processes stop sharing a disk, the worker is handed a path its host never had and the run dies with a missing file — which reads as corrupted data and sends the investigator to the wrong layer entirely. The reference is self-describing, so a worker configured for one backend that meets a reference from the other refuses by name instead of guessing. And because a local reference cannot survive scaling past one machine, the config refuses to boot in production with the local backend at all.

Creating a run: the order of operations is the design

POST /datasets/{id}/analyses with a list of model keys and a seed returns 202 Accepted. What happens inside happens in a deliberate order:

  1. The analysis_runs row is written and committed first, with status QUEUED, the requested models, the seed, and the engine version.
  2. Only then is the job enqueued to Redis (off the event loop — the Redis client is synchronous, and a blocking socket on the loop is the same defect class as blocking CPU).
  3. If enqueueing fails, the API returns 503 — but leaves the row QUEUED. The durable record says what was requested; an operator can re-enqueue. The reverse order would risk a job with no row, work the system cannot account for.

The job payload is just the run id. Everything else — which file, which models, which seed — is read back from the database by the worker, so the queue never holds state that could disagree with the durable record. One structural nicety: the enqueue call passes the imported task function object, not a dotted-string name, so renaming the task breaks at import time in the API rather than at dequeue time in the worker.

The worker: one job, executed honestly

The worker dequeues, loads the run row, marks it RUNNING with a start timestamp (this is the moment the browser's badge changes), fetches the CSV by its storage reference, and calls run_analysis() — the orchestrator you met throughout Parts 4–8. Its contract has three clauses that define the tool's failure behaviour:

  • A failed diagnostic does not fail the run. Each statistic is attempted independently; a failure is recorded as {diagnostic, error} in the output, with a closing note that the absent numbers “are not zero and not reassuring”. A run must never report fewer diagnostics than it attempted without saying so.
  • A failed run keeps nothing. Any exception in fitting or setup marks the run FAILED with the reason. There is no path on which partial results masquerade as complete ones — the mirror image of the non-convergence-is-fatal rule from Part 4, applied at the process level.
  • Jobs are idempotent. The worker re-reads the CSV by reference and overwrites results on a re-run, so a lost or stuck job is an operational nuisance, not data loss.

On success the worker writes the fits (one row per model, with per-item parameter rows), the full diagnostics payload as a JSON blob, and the run-level notes, then sets SUCCEEDED. Parameter columns are nullable on purpose: an unconverged fit is stored as unconverged, because storing 0.0 where an SE was never estimated is how a report ends up claiming certainty it does not have — Part 1's “absence must not look like a value”, enforced by the schema.

Access control has a subtlety here. HTTP handlers reach runs through an owner-scoped repository that cannot see other users' rows. The worker, which has no user, uses a separate class named SystemRunAccess — deliberately named apart, so unscoped access is a visible import in a review diff rather than an optional argument someone forgets to pass.

How the browser finds out: polling the durable record

There are no websockets. The run page polls GET /analyses/{id} every two seconds and stops when the status reaches succeeded or failed. The endpoint reads the database row — never the queue — which buys a property worth more than push latency: status survives restarts of the worker, the API, and the browser alike. The page itself tells the user it is safe to leave and come back. Results are fetched only after success; asking for them earlier returns 409, not an empty report.

Two renderings of the results exist. The web UI reads the JSON results endpoint and renders the dossier, fit tables and DIF screens as interactive sections. Separately, GET /analyses/{id}/report returns a self-contained HTML report rendered server-side with Jinja. The report is never stored: it is re-rendered from the persisted results on each request, so a template fix retroactively improves every past run's report — nothing is ever recomputed, only re-presented. The template runs with StrictUndefined, so a renamed field fails loudly at render time instead of becoming a silently blank cell.

The tests, tiered by what they can prove

Part 4 ended with “how anyone knows this is right”; here is the machinery behind that claim, and its honest current state.

TierWhat it provesWhen it runsStatus
Tier 1 — parameter recoveryThe estimator gets back parameters from data it simulated itself, for all seven families, plus SE calibration, missing data, and the refusal pathsEvery push; gates mergesRunning and passing
Postgres integrationAPI routes, the worker pipeline, storage and config against a real PostgreSQL, including applying and reversing the migrationEvery pushRunning and passing
Tier 2 — agreement with R's mirtThe same fixed datasets fitted by an independently written estimator match within tight tolerances (e.g. 2PL b within 0.06)Weekly schedule + manual triggerHas never run

Tier 2 exists because Tier 1 has a blind spot: simulator and estimator share this project's assumptions, so a shared misunderstanding of, say, the PCM would still “recover” perfectly. Fitting the same data with mirt — two programs, two languages, two authors, one likelihood — closes that gap, and is exactly what the International Test Commission guidelines ask of new analysis software. The tolerances are far tighter than Tier 1's because both programs maximise the same likelihood; residual disagreement is quadrature and convergence, not sampling error. R is not a runtime dependency — the tests skip when the reference file is absent, and there is no R in the Docker image.

Tier 2 has never actually run — and the repo says so

Two causes, both now recorded in PROGRESS.md rather than discoverable by surprise: the fixture CSVs were excluded by a .gitignore rule until recently, and GitHub fires scheduled workflows only from the default branch, which this branch has not reached. So “agrees with mirt” is currently a claim about code that has been read, not a job that has passed. The first scheduled run after merge is the thing to check. Two adjacent caveats in the same spirit: no automated test has ever had a real RQ worker dequeue a real Redis job (tests use fakeredis; Docker Compose is the only place that path executes), and no test has talked to a real S3 endpoint (moto in tests, MinIO in Compose).

Configuration: the traps worth knowing in advance

All backend settings are environment variables with the prefix IRTBOSS_; unprefixed variables are silently ignored, which is precisely the mistake that broke the v1 compose file. The ones that bite:

SettingDefaultThe trap
IRTBOSS_ENVIRONMENTdevelopmentControls the Secure cookie flag and the production refusals. A staging deploy left at development serves session cookies over plaintext while otherwise working perfectly. Set it to production on every deployed environment, staging included.
IRTBOSS_SECRET_KEYa placeholderThe placeholder is rejected at startup in production — the app refuses to boot rather than sign sessions with a public string.
IRTBOSS_STORAGE_BACKENDlocallocal is likewise refused in production, for the shared-filesystem reason above. s3 requires a bucket; S3 credentials are read by boto3 from the standard AWS variables, never by this application.
IRTBOSS_CORS_ALLOW_ORIGINSthe Vite dev origin* is rejected by a validator — a wildcard with credentialed requests is a browser-enforced contradiction anyway.
Upload caps25 MiB · 100k rows · 1k columnsThese exist and return 413/422. A per-user quota is described in the architecture document but does not exist in code — do not rely on it.

In development the frontend talks to the API through Vite's proxy so the session cookie stays same-origin (SameSite=Lax needs no relaxation). The proxy targets 127.0.0.1:8000 explicitly rather than localhost — on IPv6-preferring machines Node resolves localhost to ::1 first and does not fall back, so a v4-only API becomes unreachable from the dev server while curl, which tries both, works — a genuinely misleading failure. Under Docker Compose the target is the api service instead, via VITE_PROXY_TARGET.

Deployment, and the gaps that are documented rather than hidden

The frontend deploys to Vercel as static files with an SPA rewrite. The API and worker deploy to Fly.io (Railway is the documented alternative) as two processes of one image; the release step runs the database migration; the health check probes a liveness endpoint that deliberately makes no database round trip. Postgres and Redis are managed services. The local equivalent is one Compose file that runs the whole stack — including MinIO standing in for S3, so the storage path you exercise locally is the one that deploys.

Finally, the known gaps, in the open where they belong: login rate limiting is per-process (N instances multiply the effective limit; a Redis-backed limiter exists in the code but is deliberately unwired so login does not fail when Redis is down). CSRF is defended for cookie-authenticated mutations but login CSRF is not: a request with no session cookie is exempt, having no session to hijack, so a victim can still be forced into an attacker's account. Session revocation is all-or-nothing — one timestamp per account cannot end one device's session and keep another's — and plain logout stays local to the browser that calls it, leaving a bearer token valid for the rest of its 12-hour TTL. A job killed at the 1-hour timeout leaves its run stuck at RUNNING with no automatic reaper. And the Fly and Compose object-storage configurations have been verified by reading, not by running — the authoring machine has no Docker. Every one of these is in DEPLOYMENT.md or PROGRESS.md; the project treats “documented limitation” and “hidden defect” as different moral categories, and so should you.

What you now know

  • One image, two processes: the API never estimates, the worker does nothing else, and lazy imports keep numpy out of the web process entirely.
  • Run status lives in PostgreSQL; Redis carries only job ids; the browser polls the durable row every two seconds and survives any restart doing so.
  • Files are stored by self-describing reference (local: / s3://), never by path, so a mis-deployment fails by name instead of masquerading as data corruption.
  • The run row is committed before the job is enqueued, and an enqueue failure leaves an accountable QUEUED row behind a 503.
  • A failed diagnostic is recorded inside a successful run; a failed run keeps nothing; unconverged fits are stored as unconverged, with nullable columns so absence can never impersonate a value.
  • Reports are re-rendered from persisted results on every request — template fixes apply retroactively, and StrictUndefined makes a renamed field fail loudly.
  • Tier 1 (self-recovery) and the Postgres integration tests run on every push; Tier 2 (independent agreement with mirt) is built, scheduled — and has never run, which the repo states plainly.
  • Sessions are Argon2id-backed signed cookies whose fingerprint dies with a password change; ownership is a column on every row; other users' runs return 404, not 403.
